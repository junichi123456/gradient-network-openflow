# 対戦（PvP）仕様 — 設計メモ

レベル50固定・6匹登録／4匹選出の対人戦を実装するための仕様と、現行コードとの
差分をまとめたもの。**技リストと learnset は完成済みとみなし、ここでは触らない。**

---

## 1. 確定仕様

### 前提

- learnset 内の技は**レベルキャップに関係なく変更可能**（対戦では習得レベルを見ない）
- 対戦時はすべてのパルが**レベル50**に調整される

### 対戦の流れ

| # | フェーズ | 内容 |
|---|---|---|
| 1 | パーティ登録（構築） | 6匹。**同一種族不可**。持ち物は1匹1つ、**重複不可**。**技4つもここで確定する** |
| 2 | 対戦受付 | 待機 |
| 3 | 相手party開示 | **種族のみ**開示。技・持ち物は非開示 |
| 4 | 選出 | 6匹から4匹。**制限時間50秒**。両者完了か時間切れで次へ。時間切れ時は登録順の昇順で自動選出。**技と持ち物は構築段階で確定済みなので、ここでは触らない** |
| 5 | 配置 | 自陣は縦2×横3の6マス。そこへ4匹を**自由配置**。**上列が相手と対面** |
| 6 | 対戦 | **20分**。片方が全滅で生存側の勝ち。時間切れで両者生存なら引き分け |

### 盤面

- **8行（縦）×7列（横） = 56マス**。自陣・敵陣の2×3ブロックを**中央に配置**する
- 選出した4匹は**全員が盤面に出る**。控えがいないので**交代は発生しない**
- 座標は**論理座標を1つだけ**持つ。論理座標では常に自陣が下（Yが大）、
  敵陣が上（Yが小）。**描画側が自分の陣営を下に見せるため、相手視点では
  盤面を180度回転して描く。**ロジックは1つの向きしか知らない
  （`BattleBoard.ToViewOf`）

### 対戦中の進行

- **ターン** = パル1匹の行動。**サイクル（一巡）** = 全員が1回行動した単位
- 1ターンにつき、両陣営が1匹ずつ指定して行動を決定 → その後、行動順に従って処理
- **指定するパルと行動はどちらも伏せて同時に決める**
- 4匹選出なので **1サイクル = 4ターン = 8回の行動**
- 1サイクル中、各パルは**1ターンだけ**行動する。1ターン目に動いたパルは
  2〜4ターン目は行動できない。4ターン目に動けばそこでサイクル完了なので、
  2サイクル目（=5ターン目）から再び行動できる
- **味方は全て自分で操作する。自動処理による行動は行わない**
- **移動も1ターンの行動として選べる**（迷宮と同じ）

### 行動順の決定

1. **優先度**が高いパルが、合計種族値にかかわらず先に行動する
2. 優先度が同じなら、**そのターンに指定された2匹**のうち合計種族値（BST）が低いほうが先
3. BST も同じならランダム

**優先度を持つ技はヘッドバット（無・物理・威力40・Adjacent）の +1 のみ。**
他は技・特性・持ち物に今後配布する。

### 持続時間の扱い

| 対象 | 単位 |
|---|---|
| 天候（6技すべて20ターン） | **ターン**のまま。1サイクル=4ターンなので **5サイクル**分 |
| 状態異常 | **サイクル** |
| ランク減衰 | **サイクル** |

## 2. 射程は改造不要で成立する

当初は対戦盤用に射程を解釈し直す作業を見込んでいたが、**アリーナを
「全マスが単一の部屋」として生成すれば、既存コードのまま意図どおり動く。**

`TargetResolver` の Room は `FloorController.GetRoomBoundsAt()` を引く。
迷宮では廊下（RoomId < 0）で null が返り単体攻撃にフォールバックするが、
**8×7の全タイルに同一の RoomId を振れば盤面全体が1つの部屋になり、
Room = 味方を除く敵4匹**が自然に成立する。決定どおりの挙動になる。

同時に、他の射程も 56マスの盤面では迷宮と同じ感覚で機能する。

| 射程 | 技数 | 8×7盤面での挙動 |
|---|---|---|
| Adjacent | 393 | 隣接1体。移動と組み合わせて機能する |
| Line | 54 | 最大7マス先まで。非貫通で最初の1体 |
| Room | 31 | 盤面全体 = 敵4匹（味方は対象外） |
| TwoTile | 27 | 2マス先まで。味方は素通り |
| Area | 18 | 3×3 = 56マス中9マス（16%）。味方も巻き込む |
| Surrounding | 1 | 自身中心3×3。**味方も巻き込む（仕様どおり）** |

設置技7種も改造不要。`AttackAction.HalfAreaTiles` は **12マス固定**で
部屋の広さに依存しないため、56マスの盤面では21%を占める。

**Line についての前回の指摘は取り下げる。** 4行盤面を前提に「TwoTile の
下位互換」と書いたが、8行なら射程差が効く。威力90以上の Line 技は9種あり
**すべて特殊技**で、特殊型の主力として機能する。

| 技 | 属性 | 威力 | 命中 |
|---|---|---|---|
| ダイヤモンドダスト | 氷 | 135 | 100 |
| ドラゴンヴェインバースト | 竜 | 130 | 65 |
| レールガン | 電 | 115 | 65 |
| オーロラカノン | 無 | 110 | 100 |
| アースクエイク | 地 | 110 | 100 |

Room と Area の威力バランスは**アイテム側で調整する**方針。

## 3. 現行コードとの差分

### そのまま使えるもの

- `DamageCalculator` / `DamageContext` — 特性・天候・状態異常・ランク補正のフックが揃っている
- HAD式は任意レベルで動く。**レベル50固定は `Level = 50` を入れるだけ**。
  既存のバランス基準値がもともとLv50基準（同種ミラーが約10発で決着）
- `TargetResolver` の射程ジオメトリ（**§2 のとおり無改造**）
- `StatusEffectManager` / `TypeChartManager` / `TraitDatabase` / `MoveDatabase` / `MoveManager`(PP)
- `FloorController` の天候・フィールド・トラップ機構

### 作り直しが必要なもの

| # | 項目 | 現状 |
|---|---|---|
| 1 | **行動順モデル** | エネルギー蓄積式。`Entity.Speed` は固定100で種族値と無関係。素早さ200なら1巡2回動くモデルで、「1巡に全員1回」と両立しない。対戦用スケジューラを別に立てる |
| 2 | **状態異常/ランクの刻み** | 現在は行動ごと（`ResolveStatusTick`）。**サイクル境界へ移す** |
| 3 | **優先度フィールド** | 582技すべてに項目なし。`moves.json` にスキーマ追加。値を持つのは当面ヘッドバット1件 |
| 4 | **持ち物** | `items.json` は6件（消耗品2・投擲1・素材3）。**持ち込み装備品は0件**。アイテム群の新規設計が必要 |
| 5 | **パーティ上限** | `PartyManager.MaxActiveParty = 2`。6匹登録→4匹選出は別モデル |
| 6 | 選出・配置・時間制限・通信対戦 | 未実装 |

## 4. 実装の順序

射程作業が消えたぶん、骨格を先に通せる。

### 第1段階: 対戦が成立する最小構成（ヘッドレス検証可能）

1. **アリーナ生成** — 8×7・全マス単一 RoomId の `FloorController`。中央に2×3ブロック2つ
2. **対戦用スケジューラ** — サイクル/ターン、伏せて同時決定、優先度→BST→ランダムの行動順
3. **Lv50固定** と 4v4 の配置
4. **優先度フィールド** — `moves.json` にスキーマ追加、ヘッドバットに +1

ここまでで、両陣営の行動を台本で与えた4v4がヘッドレスで最後まで回る。
射程・ダメージ・特性・状態異常が対戦盤で正しく動くことを機械検証できる。

### 第2段階: ルールの肉付け

5. **サイクル単位の状態異常/ランク減衰**
6. **6匹登録／4匹選出** — 同一種族禁止、時間切れ時の登録順自動選出
7. **配置フェーズ** — 自陣6マスへの自由配置

### 第3段階: 対戦環境

8. **持ち物** — 装備品の設計、重複禁止、優先度への関与
9. **時間制限・勝敗判定** — 選出50秒 / 対戦20分 / 全滅判定
10. **通信対戦**

## 5. 未決事項

### 5-1. 優先度の値域と配布量

現状はヘッドバット +1 のみ。今後 技・特性・持ち物へ配る際、**先制技を配りすぎると
BST による行動順が形骸化する**ため、learnset の共有率と同じく配布量の上限を
決めるのが安全。

### 5-2. 決定済み: 乱数はシード管理しない

命中判定・急所（`GD.Randf()`）、設置技の配置、行動順の同値決着はいずれも
素のランダム。**リプレイや再現検証はユーザー側の負担で行い、ゲーム側では
シード管理を行わない。**

## 6. 構築データモデル

技4つと持ち物は**構築段階（6匹を選定する時点）でユーザーが確定させる**。
選出フェーズは「登録済みの6匹から4匹を選ぶ」だけで、技や持ち物には触らない。
対戦中の変更もできない。

`BattleEntry` が1匹ぶんの登録内容（種族 + 技4つ + 持ち物1つ）、
`BattleTeam` が6匹ぶんをまとめて構築時の制約を機械検証する。

| 検証 | 内容 |
|---|---|
| 登録数 | 6匹ちょうど |
| 同一種族 | 重複不可 |
| 持ち物 | 重複不可（持たせない = null は重複判定の対象外） |
| 技の数 | 1〜4（`MoveManager.MaxMoves = 4`） |
| 技の重複 | 同じ技を2枠には積めない |
| 技の出所 | **その種族の learnset 内であること。習得レベルは問わない** |
| レベルキャップ | **対人戦では無視する。**learnset にある技はすべて選べる（Lv50超で覚える技も含む） |
| 実在性 | 種族・技・持ち物のIDが実在すること |
| タグ:伝説 | **1つの構築に1体まで**（下記） |
| 選出 | 登録した6匹の中からちょうど4匹。重複不可 |

時間切れ時の自動選出は `BattleTeam.AutoSelect()`（登録順の昇順で先頭4匹）。

### タグ:伝説

`SpeciesData.IsLegendary`（`species.json` の `is_legendary`）。対象は7種のみ。

| 種族 | 属性 | 合計種族値 |
|---|---|---|
| セイントール | 無 | 395 |
| ベイントール | 闇 | 395 |
| グレイシャル | 氷 | 400 |
| グレイシャドウ | 闇 | 415 |
| ネプティオス | 水 | 375 |
| ジェッドラン | 竜 | 375 |
| グランジーラ | 水 | 500 |

いずれも種族値の最上位帯（375〜500）に固まっている。**1つの構築に
「伝説」タグを持つパルは1体までしか入れられない。**

`BattleTeam.Validate()` が数えるだけの単純な規則だが、影響する場所は
思ったより多い。

- **構築画面**（`TeamBuildScreen`）: 規則チップに「「伝説」は1体まで」を追加。
  種族名の横に伝説タグの金色ピルを出す
- **種族選択画面**（`SpeciesPickScreen`）: 編集中の枠以外に既に伝説が
  居るなら、他の伝説の種族は選べない（押せない＋理由を表示）。
  同一種族が既に居るときの「パーティに登録済み」と同じ扱い
- **完全ランダム構築**（`BattleMatchScene.RandomTeam`）: シャッフル済みの
  種族列を先頭から拾う際、2体目以降の伝説だけ読み飛ばす
- **NPC対戦相手の生成器**（`Tools/generate_npc_teams.py`）: 伝説は
  種族値の最上位帯に固まっているため、種族値帯で窓を取るサンプリングだと
  2体以上まとめて拾いやすい。`enforce_legendary_limit()` が2体目以降を
  同じ窓の中の非伝説候補へ差し替える

### 機械検証

| 検証 | 結果 |
|---|---|
| 「伝説」1体は通る | OK |
| 「伝説」2体目は弾く | OK |
| （NPC生成器）タグ:伝説は1チームに1体まで | OK |
| （完全ランダム構築）毎試合とも構築規則を満たす | OK（伝説の規則も含む） |

## 7. 持ち物 16種

構築段階で1匹1つ、チーム内で重複不可。**使い切り9種**（条件を満たすと1回だけ
発動して消費）と**所有中持続7種**。

### 使い切り

| 名前 | 効果 | 接続先 |
|---|---|---|
| ガードトニック | HPが50%未満になると最大HPの25%回復 | 被弾直後の閾値判定 |
| ラストトニック | HPが33%以下になると最大HPの50%回復 | 同上 |
| エンデュアチャーム | HP満タンから即死する攻撃を受けてもHP1で耐える | `TakeDamage` 直前 |
| クリットシェル | 急所を受けた時、そのダメージを90%減 | ダメージ確定後 |
| ウィークシェル | 弱点属性を受けた時、そのダメージを75%減 | ダメージ確定後（相性倍率>1で判定） |
| ルームミラー | **相手の** Room射程を受けた時、受けたダメージを使用者へ反射 | `TakeDamage` 直後 |
| エリアイージス | **相手の** 範囲射程を受けた時、所持者以外の味方はダメージを受けない | AoE対象ループの手前 |
| ランクアンカー | 自分のランクが下がったら、**下がった分だけ**戻す | `ApplyRankTo` |
| キュアベル | 自分が状態異常になったら回復する | `ApplyAilmentTo` |

### 所有中持続

| 名前 | 効果 | 接続先 |
|---|---|---|
| リジェネバンド | 自分のターン終了時、HPを10%回復 | `BattleScheduler` のターン終了 |
| パージバンド | 自分のターン終了時、全状態異常蓄積値が100減少 | 同上 |
| パワーレンズ | 物理技の使用時、実効威力 +25%（急所時は不作用） | `PowerMultiplier` |
| フォーカスレンズ | 特殊技の使用時、実効威力 +25%（急所時は不作用） | `PowerMultiplier` |
| アイアンプレート | 物理技の被弾時、受ける技の実効威力 -30%（急所時は不作用） | `PowerMultiplier` |
| マインドプレート | 特殊技の被弾時、受ける技の実効威力 -40%（急所時は不作用） | `PowerMultiplier` |
| ワイドウォード | 全体攻撃技(Room/Area)の攻撃を受けない | 既存の無効化と同じ早期return |

### 確定した解釈

- **増減はその一撃の計算にだけ乗る**（解釈a）。被弾を機に恒久バフを得て
  累積する形ではない。
- **レンズ/プレート4種は実数値ではなく実効威力を動かす。**ダメージは実効威力に
  対して線形（`rawDamage = baseCalc * effPower/100`）なので、表記の ±25/30/40%
  がそのままダメージの増減になる。実数値(Atk/Def)側に掛けると
  `Atk²/(Atk+Def)` の非線形を通り、攻撃側は表記より強く(+25%表記が実測+39%)、
  防御側は表記より弱く(+30%表記が実測-12%)出てしまうため。
- **レンズ/プレート4種は急所時には作用しない**（§8）。
- **ルームミラー / エリアイージスは相手が使用した技のみ**に反応する。
- **ランクアンカーは下がった分だけ戻す。**全ランクを0に均すのではない。
- **エリアイージスの「範囲射程」は Area と Surrounding。**Room は元々味方に
  当たらないので対象外。所持者自身は庇わない。

### ワイドウォードの強さは意図的

Room 31技 + Area 18技 = 49技を完全無効にするが、**これは対面対戦へ構築を
寄せるための意図的な設計**。所持者が後方にいる場合、直線射程・2マス射程の
技の有意性が高まるという副次効果も狙っている。

## 8. 急所とレンズ/プレートの関係

一度「通常ダメージ → 特性 → 持ち物 → 急所」の順に処理を並べ替える案を入れたが、
**この案は撤回した。**急所は従来どおり `DamageCalculator` の Step 4 で、相性・
STAB・竜倍率と同じ乗算列の中で掛かる。

代わりに、**レンズ/プレート4種は急所時に作用しない**という仕様にした。

| 持ち物 | 非急所 | 急所 |
|---|---|---|
| パワーレンズ | 実効威力 +25% | 作用しない |
| フォーカスレンズ | 実効威力 +25% | 作用しない |
| アイアンプレート | 実効威力 -30% | 作用しない |
| マインドプレート | 実効威力 -40% | 作用しない |

既存の急所クランプ（`atkMul` の `Max(1f)` / `defMul` の `Min(1f)` /
`powerMul` の `Max(1f)`）と同じ「急所は相手の補正を貫く」考え方で、攻撃側の
増幅も防御側の軽減もまとめて無効になる。

**クリットシェル（急所を受けた時 -90%）とウィークシェル（弱点を受けた時 -75%）は
対象外で、従来どおり働く。**クリットシェルは急所でしか発動しない持ち物なので
除外できず、ウィークシェルは急所ではなく相性を条件にしているため。

## 9. 配置フェーズ

`BattleDeployment` が選出4匹とマスの対応を持ち、規則を機械検証する。
座標はすべて論理座標（相手視点の180度回転は描画側の仕事なので現れない）。

| 検証 | 内容 |
|---|---|
| 配置数 | 選出した4匹ちょうど |
| 範囲 | 自陣の6マス（縦2×横3）の内側 |
| 重なり | 同じマスに2匹は置けない |

**6マスのうちどの4マスを使うかは自由**で、前列/後列の枚数にも縛りはない。
飛び飛びの取り方も通る。自陣と敵陣は重ならない（自陣 Y4〜5 / 敵陣 Y2〜3）。

配置を決めずに進んだ場合の既定配置は `BattleDeployment.Default()`
（選出順に、相手と対面する前列から詰める）。選出フェーズの時間切れ自動選出と
対になる挙動。

### 操作は「持って置く」の2手

`BattleDeployment.Place(匹, マス)` が唯一の操作。空マスへ置けば移動、
埋まっているマスへ置けば**入れ替え**になる。

「どかしてから置く」の2手に分けなかったのは、途中に *1匹が盤外にいる*
中途半端な状態が生まれるため。入れ替えならどの瞬間も4匹が盤上に揃っていて、
**時間切れがいつ来ても配置は常に有効**——20秒の制限時間と噛み合う。

### 制限時間 20秒

`BattleClock.Deploy`。選出（50秒）と違い「未提出側を自動で決める」処理は
要らない。既定配置から始まり、どの操作をしても4匹が揃ったままなので、
締め切り時点の並びをそのまま持って対戦へ入ればよい。

## 10. サイクル単位の刻み

状態異常とランク減衰は**サイクル境界でのみ**刻まれる。
`BattleScheduler.ResolveTurn` は `ResolveStatusTick` を呼ばず、`EndCycle` が
生存している全員に1回だけ呼ぶ。

1サイクル = 4ターンなので、行動ごとに刻む迷宮側（`TurnScheduler.Tick`）と
比べて刻みの頻度が 1/4 になる。4ターン解決してもサイクルが閉じるまでは
ランクが動かないことを機械検証している。

天候だけは**ターン単位のまま**（6技すべて20ターン = 5サイクル分）。

## 11. 制限時間と決着

`BattleClock` が選出50秒・配置20秒・対戦20分を持つ。時間は Godot から直接読まず、
外から `Advance(秒)` で与える。**20分の対戦を実際に待たずに検証できる**のが
この形にした理由。

### 選出フェーズ（50秒）

- 手動提出は `SubmitSelection()`。登録6匹からちょうど4匹でなければ**拒否**する
- **両者の選出が揃えば時間内でも締め切る**
- 50秒で締め切られ、**未提出側は登録順の昇順で自動選出**（`AutoSelect()`）
- 締め切り後の提出は拒否される

### 配置フェーズ（20秒）

- 既定配置から始まるので、時間切れ時の「自動で決める」処理は不要（§9）
- 20秒で締め切り、**そのときの並びのまま**対戦へ移る

### 対戦フェーズ（20分）

`BattleClock.Resolve()` が最終結果を返す。全滅判定が最優先で、そのあとに
20分の判定が来る。

| 状況 | 結果 |
|---|---|
| 片方が全滅 | 生存側の勝ち（`PlayerWin` / `EnemyWin`） |
| 相打ちで両者全滅 | `Draw` |
| 20分が尽き、両者に生存者あり | `Draw` |
| 上記以外 | `Undecided`（続行） |

全滅と時間切れは別の場所で判定される（`BattleScheduler.Winner()` が全滅、
`BattleClock` が時間切れ）。`Winner()` が null を返すのは「両者生存」と
「相打ちで両者全滅」の2通りあるので、時計側が両方を見分けて決着を出す。

## 12. 通信対戦

### ホスト権威型にせざるを得ない

戦闘の乱数（命中判定・急所・状態異常の抽選など）は **35箇所**に散っており、
**シード管理は行わない**方針（§5-2）。したがって両者が同じ入力から同じ結果を
再現することはできず、**ロックステップ方式は成立しない**。

片側（ホスト）だけが `BattleScheduler` を回して結果を配る形にする。
クライアントは入力を送り、返ってきた結果を描画するだけで、**自分では
ダメージを計算しない**。行動順も優先度→種族値→**ランダム**で決まるため
クライアント側では再現できず、ホストが決めた順序を結果に載せて配る。

### 型で守る2つの要件

**1. 開示は種族のみ**（§1「開示されるのは種族のみであり、その技や道具などの
細部は開示されない」）

`BattleEntry` をそのまま送ると技と持ち物が漏れる。送信前に必ず
`PublicEntryView` へ落とす。この型は `SpeciesId` **しか持てない**ので、
技や持ち物を載せる場所がそもそも無い。

**2. 伏せて同時に決める**

`BattleSession` が「両陣営の入力が揃うまで伏せておく」責任を一手に持つ。

| 規則 | 実装 |
|---|---|
| 片方だけ提出では相手の手が見えない | `PeekOpponentInput()` は `BothSubmitted` が false なら必ず null |
| 二重提出の拒否 | 出し直しで相手の手を見てから変えることを防ぐ |
| 解決後は伏せ直す | `ResolveTurn()` が保留を消す |

伏せる責任がここに集約されているので、**通信層は入力をそのまま渡すだけでよい**。

### やり取りする内容

| 型 | 内容 |
|---|---|
| `PublicEntryView` | 相手に見せる編成（種族のみ） |
| `TurnInput` | どのパルが何をするか（技枠 -1 は移動） |
| `TurnResult` | 解決後の行動順・全個体のHP・決着 |

`TurnResult` は差分ではなく**HPの実値**を配る。取りこぼしがあっても次の
ターンで整合するため。

### トランスポート（`BattleNetwork`）

Godot の `ENetMultiplayerPeer` を使う。以下は一任されて決めた構成。

| 論点 | 決定 | 理由 |
|---|---|---|
| 接続方式 | **直接接続**（片方がホスト、もう片方がアドレス指定で参加） | マッチングを挟むには常時動くサーバが要り、運用費と実装が別物になる。§1-2「対戦受付」はこれで代替 |
| 権威 | ホスト | 乱数にシードを持たせないためロックステップが成立しない |
| 切断 | **投了扱い**（残った側の勝ち） | 20分の試合中に相手が落ちたまま止まると決着がつかない |
| 直列化 | 編成は JSON 文字列、ターン入力は int/Vector2I | RPC の引数は Variant 互換に限られるため |

RPC の向きで開示範囲が変わる。

- **クライアント → ホスト**（`ReceiveFullTeam`）: 技と持ち物まで含む完全な編成。
  ホストが相手のぶんも計算するため必要
- **ホスト → クライアント**（`ReceivePublicTeam`）: 種族だけ。
  `EncodePublic()` は `SpeciesId` しか詰めないので漏れる余地がない

### 正直に書いておく限界

**ホストは相手の技と持ち物を計算のためにメモリ上に持つ。**人間に表示はしないが、
ホスト側を改造すれば覗ける。これはホスト権威型に本質的な穴で、塞ぐには中立な
サーバが要る。友人同士の対戦を想定した割り切りとして受け入れている。

### 実地検証

`Scenes/NetTestScene.tscn` を2プロセス立てて localhost で繋ぐ。

```
godot --headless Scenes/NetTestScene.tscn -- --host
godot --headless Scenes/NetTestScene.tscn -- --join
```

| 検証 | 結果 |
|---|---|
| 接続が成立する | OK |
| ホストが相手の完全な編成を受け取る | OK（6匹すべて技4つ） |
| クライアントには種族しか届かない | OK（`OpponentFullTeam` が null のまま） |
| ターン入力がホストへ届く | OK |
| 相手だけの提出では伏せたまま | OK |

### 残っている作業

マッチング（相手を探す仕組み）は直接接続で代替しているため未実装。
選出・配置フェーズの RPC も未配線（`BattleClock` / `BattleDeployment` 側の
ロジックは揃っているので、`TurnInput` と同じ形で送るだけ）。

`BattleFlow` と `BattleNetwork` もまだ繋がっていない。**繋ぐ場所は1点**で、
`BattleFlow.AdvanceTurn` が相手の `TurnInput` を得るところ。いまは
`ScriptedOpponent.Decide()` が返しているので、ここを受信した入力に
差し替えれば通信対戦になる（`BattleSession` から先は変更が要らない）。

## 13. UI

設計案: https://claude.ai/code/artifact/41acd521-620b-4318-8487-32c442fb1a84

### 貫いた原則

**色を持つものは意味を持つものだけ。** 面と枠は無彩色に寄せ、彩度を持つのは
**陣営（青／赤）と属性9色**に限る。盤面の情報量が多いので、色が散ると視線が迷う。
属性9色は move_editor / learnset ビューアと同じ16進を `BattleTheme` に置き、
3つのツールで見た目が揃うようにした。

**HPは数値ではなく二層の帯。** 実HPの下に直前の値を赤で残す（`HpBar`）。
静止した画面からでも「さっき何点入ったか」が読める。対戦中いちばん見る場所。
回復時は ghost を即座に追従させる — 赤い帯が残ると「減った」と誤読されるため。

**種族値を隠さず並べる。** 「合計種族値が低いほど先に動く」は他所にない規則
なので、行動順レールに数値をそのまま出し、左ほど先に動くことを見せて覚えて
もらう。優先度つきの技はここへ割り込む。

**伏せられている事は伏せられていると見せる。** 相手の技・持ち物は空欄ではなく
破線と `?` で示す。相手の状態も「選択中…／決定済み」の2値だけ出し、中身は
解決まで見せない。

### 制約

**日本語UIなので書体で個性は出せない。** 日本語フォントを埋め込むと数MBに
なるため、OS標準の日本語スタックを使い、数値だけ等幅＋桁揃えにする。
余白・階層・色の使い分けで差をつける方針。

### 実装状況

| 画面 | 状態 |
|---|---|
| 対戦 | `BattleHud` — 上部バー / 行動順レール / 8×7盤面 / 右カラム |
| 構築 | `TeamBuildScreen` — 左に6枠／右に1匹の中身（種族・技4つ・持ち物）を編集 |
| 種族選択 | `SpeciesPickScreen` — 287種を属性で絞って選ぶ |
| 選出 | `SelectionScreen` — 相手6匹（種族のみ）／自分6匹から4匹 |
| 配置 | `DeployScreen` — 自陣6マスと、**すべて「?」の敵陣6マス**／下段に自分の4匹の詳細 |

共通部品は `BattleTheme`（配色）、`HpBar`（二層のHP帯）、`BattleUiKit`
（属性チップ・分類チップ・規則行などの小物）。

**規則の判定はUI側に書き直さない。** 構築画面の充足表示は
`BattleTeam.Validate()` の結果をそのまま出し、配置画面の開始可否は
`BattleDeployment.Validate()` を見る。UI側で判定を再実装すると、
生成器と検証器が食い違ったときと同じ事故になる。

### 実機での確認

`Scenes/BattleFlowScene.tscn` が入口。構築 → 相手マッチング → 選出 → 配置 → 対戦 を通しで触れる。

```

```

撮影用の経路もある（起動直後の画面を保存して終了）。

```

```

`--phase` は `build` / `selection` / `deploy` / `battle` / `command`。
`command` は技を選んだ直後（射程が盤面に出ている状態）を撮る。

### 実機でしか出なかった不具合

ヘッドレス検証（ノードが生える／押すと状態が変わる）は全部通っていたが、
描いてみると4件崩れていた。**レイアウトはノードの有無では検証できない。**

| 症状 | 原因 |
|---|---|
| UI全体が左上へ潰れる | `SetAnchorsPreset` は**現在の矩形（=0）を保つ**。`SetAnchorsAndOffsetsPreset` でないと親を埋めない |
| 盤上のユニットが細い線になる | **`Button` は `Container` ではない**ので、子を足しても広がらない。全面へ貼り付ける必要がある |
| 対戦画面が固まる | 毎フレーム盤面を作り直していた（1フレームに数百個の stylebox）。時計だけの更新と分けた |
| シーンが起動時に落ちる | `.tscn` のルート型が `Node2D` のままでスクリプトの `Control` と食い違い |
| 盤面が左詰めになる | `GridContainer` に `ExpandFill` を与えても**広がるのは矩形だけ**で中身は左上に寄る。`ShrinkCenter` にして `Alignment.Center` の箱へ入れる |
| 画面の縁で文字が切れる | ルートを `FullRect` で貼ると余白が0になる。オフセットで縁を空ける |
| 配置画面で技と持ち物が画面外へ落ちる | 中央（盤面）が `ExpandFill` で下段を押し潰していた。下段に必要な高さを与える |

あわせて、**技を選んでも提出ボタンが無効に戻り永久に提出できない**バグも見つけた。
選択のたびにパネルを組み直す際、ボタンを固定で `Disabled = true` にしていた。
有効/無効を選択状態から引くようにした。

`QueueFree` は解放がフレーム末まで遅れるため、作り直しの瞬間に古いノードと
新しいノードが同居する。`BattleUiKit.ClearChildren` でツリーから即座に外す。

**同じ性質でもう1件、無限ループを踏んだ。**戦闘ログの行数を抑える処理が

```csharp
while (_log.GetChildCount() > 8) _log.GetChild(0).QueueFree();
```

だった。`QueueFree` は子から外さないので件数が減らず、**フレームが来るまで
永久に回る**。実機ではフレームが挟まるので表面化しなかったが、1フレーム内で
複数行を吐く通し検証で完全に停止した。ツリーからは即座に外し、解放だけを
遅らせる形へ直した。

## 15. 入力の配線とフェーズ進行

### `BattleFlow` が進行を握る

画面は自分の描画にしか責任を持たず、**フェーズの遷移は `BattleFlow` だけが握る**。
状態（選出・配置）も Flow が持つので、画面を捨てて作り直しても失われない。

```
構築 → 相手マッチング → 選出(50秒) → 配置 → 対戦(20分) → 決着
```

**構築を相手マッチングより先に置く。**NPC対戦相手を導入したとき（§16）
「相手選択 → 構築」の順で実装したが、これは§1の対戦の流れ（構築が
フェーズ1、相手開示がフェーズ3）と食い違っていた。6匹をどう組むかは
相手を知らずに決めるものなので、正しい順は構築が先。`BattleFlow.Begin()`
は常に `Phase.Build` から始まり、`ConfirmBuild()` が相手マッチングへ、
`ChooseOpponent()` が選出へ進める。

時間切れの既定動作は `BattleClock` に実装済みなので、Flow はそれを呼ぶだけ。
選出が50秒で締め切られたら登録順の昇順で自動選出し、そのまま配置へ移る。

### 押せるもの

`BattleUiKit.ClickableCard` は `Button` を土台にしている。**フォーカス枠と
キーボード操作がただで付いてくる**のが理由で、見た目を `Card` と揃えるために
4状態すべてに stylebox を入れて Godot 既定のボタン外観を上書きしている。

| 画面 | 押せるもの | 効果 |
|---|---|---|
| 構築 | 「対戦を受け付ける」 | 規則を満たしていれば選出へ。満たさなければ無効 |
| 選出 | 自分側の行 / 「決定して伏せる」 | 4匹まで選択。4匹揃うまで決定は無効 |
| 配置 | 自陣のマス / 下段のカード / 「この配置で開始」 | 持つ→置く。敵陣は押せない（情報が無いので操作対象にしない） |
| 対戦 | パルの一覧・盤上の自分のパル / 技・移動 / 盤面のマス / 「決定して伏せる」 | ①②③（下記） |

**提出は「決定して伏せる」を押すまで起きない。**技を選んだだけでは射程が
出るだけで、相手には何も伝わらない。

### 対戦中の1ターンは3段

```
① 操作するパルを選ぶ → ② 行動と狙う先を選ぶ → ③ 伏せて提出 → 相手待ち → 解決
```

**①を独立した段にしたのは、どのパルを出すかが読み合いの一部だから。**
「まだ動いていない4匹のうち誰を出すか」は行動そのものと同じ重みの選択で、
`TurnInput` も `ActorIndex` と `MoveSlot` を対等に持っている。自動で
決めてしまうと、その選択肢が存在しないのと同じになる。

②で選べるマスは射程の形で変わる。

| 射程 | 選べるマス | 指した結果 |
|---|---|---|
| 隣接 | 隣の8マス | そのマスの1匹へ |
| 直線 / 2マス | 8方向の射線上すべて | 指した方向へ**向きが決まる** |
| 範囲 | 盤面全マス | そこを中心に3×3 |
| 周囲 / 部屋 / 全体 | **なし** | 狙う先を持たないので即提出可 |
| 移動 | 隣の8マス（歩けて空いているもの） | 1ターン1マス |

選べるマスと、実際に当たるマスは別物として描き分ける。前者は候補、後者は
指した1マスから決まる着弾の形（`BattleFlow.SelectableTiles` / `Preview`）。

③の「待つ」は飾りではない。`BattleSession` が両者の入力を伏せたまま抱え、
揃うまで解決しないので、**待たなければ盤面は1マスも動かない**。

> 通信対戦がつながるまでは `ScriptedOpponent` が相手役を務める。
> 強さは目的ではなく、`BothSubmitted` に到達させて③を成立させるためだけの
> 代役で、`BattleNetwork` が相手の入力を運ぶようになったら外れる。

### 相手が誰を操作しているかも伏せる対象

行動順レールは全個体の種族値と「行動済／未行動」を出す——どちらも解決を
見ていれば分かる公開情報。一方、**「このターンに誰を操作するか」は伏せて
同時に決める対象**なので、「操作中」と名指しできるのは自分が選んだ1匹だけ。
相手側には、提出済みであっても付かない。

### 機械検証

画面が生えるかではなく、**操作すると状態が変わるか**を見ている。
ボタンを実際に押し、時計を進めてフェーズが進むことを確認する。

| 検証 | 結果 |
|---|---|
| 最初は構築画面 | OK |
| 規則を満たす構築なら選出へ進める | OK |
| 行を押すと選出に入る | OK（0 → 4匹） |
| 決定を押すと配置画面へ | OK |
| 配置画面でマスを押すと配置が変わる | OK |
| 埋まっているマスへ置くと入れ替わる | OK（4匹維持） |
| 配置画面に自分の技が出る | OK |
| 開始を押すと対戦画面へ | OK |
| 対戦は操作するパルの選択から始まる | OK |
| パルを選ぶと行動パネルへ移る | OK |
| 「操作中」の名指しは自分の1匹だけ | OK（1件） |
| 狙う先を選ぶまで提出できない | OK |
| 提出しても相手が出すまで解決しない | OK |
| 両者が出すとターンが解決する | OK（ターン 0 → 1） |
| 解決後は次のパルの選択へ戻る | OK |
| 選出が時間切れなら自動で配置へ | OK |
| 配置が時間切れなら現在の配置のまま対戦へ | OK |

## 16. NPC対戦相手

マッチング（人の相手を探す仕組み）はまだ実装できる段階にないので、対戦の
相手はNPCが務める。8人を `Data/npc_teams.json` に置き、対戦の入口で選ぶ。

```
構築 → 相手マッチング → 選出(50秒) → 配置(20秒) → 対戦(20分)
```

### 人の相手と同じ入口しか使わない

これが設計上の要点。NPCが下す決定は3つあるが、いずれも人の側と同じ経路を通る。

| 決定 | 通る経路 |
|---|---|
| 選出（6匹→4匹） | `BattleClock.SubmitSelection()` |
| 配置（自陣6マスへ4匹） | `BattleDeployment` |
| 毎ターンの行動 | `TurnInput` を `BattleSession.SubmitInput()` へ |

盤面を直接触る近道は持たない。**`BattleSession` から先は、相手が人かNPCかを
知らない。**通信対戦が入るときに差し替わるのは `BattleFlow.AdvanceTurn` の
1行——`_npc.Decide()` を受信した `TurnInput` に置き換えるだけで済む。

選出と配置は**対戦が始まる前に決めきる**（`NpcOpponent.Prepare`）。人の側と
同様に相手の選択を見ないまま決めるので、伏せて同時に決める規則がそのまま
成り立つ。画面へ渡す口も作っていないので、開示範囲（§14）も崩れない。

### 編成は生成する

1人につき技4つ × 6匹なので、8人ぶんで192件になる。手書きでは learnset 外の
技を混ぜる事故が必ず起きるし、learnset を作り直すたびに全部が腐る。

```
python3 Tools/generate_npc_teams.py   # Data/npc_teams.json を作る
python3 Tools/verify_npc_teams.py     # 構築規則を検証する
```

相手ごとに主属性を決め、その属性を持つ種から6匹を採る。技は「自属性の
最大威力 → 打点の重ならない他属性 → 残りの威力順」で4つ。持ち物は6匹ぶんを
重複しないよう配る。

**強い順に採ってはいけない。** 最初にそうしたところ、いちばん弱い相手でさえ
1匹あたりBST350超になり、初期のパル（BST210〜265）では初戦から手が出な
かった。相手ごとに狙う種族値帯を変え、1匹あたり226→359の階段にしてある。

| 相手 | 主属性 | 合計種族値 | 1匹あたり |
|---|---|---|---|
| ほのおつかい コウ | Fire | 1360 | 226 |
| みずつかい ナギ | Water | 1490 | 248 |
| くさつかい モエ | Grass | 1600 | 266 |
| でんきつかい ライ | Electric | 1695 | 282 |
| こおりつかい ユキ | Ice | 1885 | 314 |
| じめんつかい ダイ | Ground | 1995 | 332 |
| あくつかい クロ | Dark | 2130 | 355 |
| ドラゴンつかい リュウ | Dragon | 2155 | 359 |

読み込み側（`NpcTeamDatabase`）でも `BattleTeam.Validate()` を通し、**規則を
満たさない相手は対戦に出さない**。生成器の不具合を黙って弱い相手として
出すより、気づける形で落とすほうがよい。

### 選出の選び方——相手の6匹（種族のみ）を見て決める

選出フェーズの時点で、相手の6匹は**種族だけ**開示されている（技・持ち物・
配置は依然として不明——§14）。人の側は `SelectionScreen` でこれを見ながら
選べるのに、NPCは長らく相手を一切見ず、自分の合計種族値と最大威力
だけで上から4匹を採っていた。見えている情報を使わないのは片手落ちなので、
NPCの選出にも同じ情報を渡すようにした。

```
NpcOpponent(profile, faction, foeView: BattleSession.DiscloseTeam(相手の6匹))
```

`foeView` が無い（＝相手がまだ分からない）場合は従来どおり種族値+威力の
順。ある場合は6匹それぞれに、相手6匹との相性を足し込んだ得点を付ける。

```
相性 = Σ 相手1匹ごとに (
    自分の最強打点 × 相手の属性への相性倍率      … 通りやすさ
    − 相手の属性(≒相手のSTAB)が自分に通る倍率 × 40  … 受けやすさ
)
選出スコア = 合計種族値 × 0.5 + 相性 + 乱数(タイブレーク用)
```

技・持ち物・配置は分からないので、見えている「種族の属性」だけから
双方向の相性を見積もる。相手の自属性を「相手のSTAB」とみなすのは
NPC生成器・`DefaultLoadout` 自身が「自属性の最大威力を主力にする」と
いう選び方をしているため、こちらの持つ前提を相手にもそのまま当てはめて
矛盾がない。

この変更は選出だけに閉じており、`BattleFlow.ChooseOpponent` と
`BattleMatchScene.RunMatch` の双方で、対戦相手の開示済み編成を
`NpcOpponent` のコンストラクタへ渡すよう直しただけ——技の選び方
（`DefaultLoadout`）や毎ターンの行動判断（後述）には手を入れていない。

### 行動の選び方

出せる全員 × 技4つ × 狙える全マスを総当たりして、最も得点の高い1手を採る。
盤面は56マスなので候補は高々数百で、素直に全部見たほうが「なぜその手を
選んだか」を追える。移動（技を使わず1歩詰める/離れる）も候補に含める。

得点は「攻撃の得点 − 留まる/移動先の生存ペナルティ」。

```
攻撃の得点 = Σ (威力 × 相性倍率 × 命中率)          … 敵に当たるぶん
              − Σ (同上) × 1.5                    … 味方を巻き込むぶん
              + 120                                … 倒しきれる相手ごと

生存ペナルティ = 60 × min(被弾見積り ÷ 現在HP, 1.3)²
                 × max(0.25, 1 − サイクル数 × 0.04)   … 切迫度
```

実ダメージ計算は通さない。副作用があるうえ、**相手の持ち物やランクまで
読めてしまう**（NPCが知り得ない情報で判断することになる）。撃ち分けの
判断には相性と威力で足りる。

誰にも当たらないなら、最も近い敵へ1歩詰める（生存ペナルティを差し引いた
上で）。

**「指せるマス」の規則は人と共有する**（`BattleTargeting`）。別々に持つと、
UIでは選べないマスをNPCだけが撃てる——あるいはその逆——という食い違いが
必ず起きる。learnset の生成器と検証器が別々に規則表を持って事故った、
あれと同じ構図。

#### 生存ペナルティ——常に殴るだけではない

以前は攻撃の得点だけで手を選んでいたため、**倒されそうでも常に攻撃を
選び、退く・様子見するという選択肢が存在しなかった**。全滅させることと
同じくらい、生き残ることも対戦では重要という指摘を受けて追加した。

まだ行動していない敵全員について、持っている攻撃技のうち最大の被弾量
（威力×相性倍率×命中率、PP切れ・威力0の技は除く）を、留まる場合／各移動先
それぞれについて見積もる（`EstimateThreat`）。複数の敵から狙われる場合は
合算する（1体からは最大威力の技1発分だけを見る——同じ相手から同じサイクル
内に何度も撃たれることはないため）。

見積もった被弾量を現在HPに対する比で正規化し（上限1.3倍——瀕死でも極端に
過大評価しない）、2乗してペナルティ化する。2乗にしているのは、
「半分削られる」と「即死級」の差を単純な比例よりはっきり分けるため
——半分程度の被弾は多少気にする程度、致死級の被弾は攻撃よりよほど優先して
避けるべき、という段差を作る。

**サイクル数に応じて切迫度を減衰させる**（最大75%減、25%未満にはしない）。
これが無いと、双方が「攻撃するより退くほうが得点が高い」と判断し続け、
どちらも攻め手を欠いたまま睨み合いが長引く——実際、この減衰を入れる前は
平均決着サイクルが16.1（生存ペナルティ導入前の約3倍）まで伸び、
600提出の上限に達して未決着になる試合も出た。長引くほど「悠長に構えて
いる場合ではない」という圧力が強まるようにすることで、決着へ収束する
力を残しつつ、序盤〜中盤の危険回避は機能させている。

**範囲「自分の周囲」を全体攻撃と誤認する不具合。** 被弾見積りの実装当初、
`BattleTargeting.SelectableTiles` が空リストを返す射程（部屋全体・盤面
全体・自分の周囲の3種類）をすべて「盤面のどこにいても当たる」として
扱っていた。部屋・盤面全体はそれで正しいが、**自分の周囲（3×3）は
違う**——射程が狭いのに盤面全体からの脅威として扱われ、AIが過剰に
退がる原因になっていた。自分の周囲だけは、技の使い手を中心にした3×3
マスを実際に計算する特別扱いを追加して直した。

### 選出はここで初めて盤面に届く

以前は画面を出す前に既定配置でパルを立てていたため、**選出画面で別の4匹を
選んでも盤面は最初の4匹のまま**だった。選出 → 配置 → 生成の順にすれば
食い違いようがないので、パルを立てるのは対戦へ入る直前にした
（`BattleArena.Spawn`）。

## 17. 通し試合の測定

部品ごとの検証とは別に、**1試合を全滅まで回す専用の入口**を置いた。
持ち物の有無・相手・試合数を替えて何度でも回せる。

```
godot --headless --path . Scenes/BattleMatchScene.tscn -- \
      --home player --away npc_fire --matches 20 [--items both|home|away]
```

`--items` を付けない限り**両陣営とも持ち物を全部外す**。片側だけに持たせる
こともできる（持ち物がどちらを利しているかの切り分け用）。
1試合目だけターンごとの盤面要約を出し、残りは勝敗の集計だけを出す。

### 見つけた不具合: 範囲技が指定と別の場所へ落ちていた

`AttackAction.ExecuteAoe` は着弾中心を**主対象（狙ったマスに立っている個体）
から引いていた**。迷宮では狙う先が「目の前の1体」しか無いので正しいが、
対戦は盤面のマスを直接指す——しかも**範囲技は空マスを中心に複数を巻き込む
ために使う**。空マスを指すと主対象が居ないので、着弾は「使用者の向いている
先」へ落ちていた。画面に出した3×3の予告と実際の着弾がずれる。

`AttackAction` に着弾中心を明示的に渡せるようにし、対戦は狙ったマスを
そのまま渡す。指定が無いときの経路は元のままなので、迷宮側は変わらない。

### 測り方の落とし穴: 選出と配置を揃えないと比較にならない

最初の測定は3組すべてが 0勝20敗——**後手側が全勝**した。同じ編成どうしの
ミラー戦でも4勝16敗で、盤面か行動順に非対称があるように見えた。

原因は測定側だった。自陣だけ「登録順の自動選出＋既定配置」で回し、敵陣は
NPCの判断（種族値と最大威力で4匹、隣接技の比率で前後を決める）を使って
いた。**差は編成ではなく、選出と配置の決め方**だった。

裏を返すと、**選出と配置の決め方だけで勝率が25%まで落ちる。**
盤面の配置がそれだけ効くということでもある。

### 手持ちの技の選び方が壊れていた

自陣は最弱の相手にも20戦全敗した。原因は編成ではなく技で、構築画面が
編集に対応するまでの仮置きが `learnset` の先頭4件を採っていた。
**learnset はレベル順なので、先頭はレベル1の技**——威力15が2つと変化技が
2つ、という組み合わせになる。相手は威力90〜135を持つので勝負にならない。

NPCと同じ選び方（`DefaultLoadout`、生成器の `pick_moves` と同じ規則）に
揃えた。自分と相手で技の選び方が違うと、結果が「どちらの選び方が良いか」に
なってしまい、編成やプレイの差が見えなくなる。

| 手持ち6匹 vs（持ち物なし・各20試合） | 修正前 | 修正後 |
|---|---|---|
| ほのおつかい コウ（相手1人目） | 0勝20敗 | 8勝12敗 |
| みずつかい ナギ（相手2人目） | 0勝20敗 | 0勝20敗 |
| ドラゴンつかい リュウ（相手8人目） | 0勝20敗 | 0勝20敗 |

相手1人目とは互角になった。ただし**2人目で既に歯が立たない**ので、階段の
傾きは想定より急。相手側の種族値帯を詰めるか、手持ちの既定編成を見直すかは
構築画面が編集に対応してから決める。

### 持ち物は勝敗を決めるほど重い

同じ編成どうしのミラー戦で、持ち物を持つ側を変えて30試合ずつ。

| 持ち物 | 自陣 | 敵陣 | 引き分け |
|---|---|---|---|
| なし | 12 | 18 | 0 |
| 自陣のみ | 10 | 19 | 1 |
| 敵陣のみ | 2 | 28 | 0 |
| 両方 | 0 | 29 | 1 |

**持っている側が93%勝つ。**編成も技も同一なので、差は持ち物だけ。

内訳を追うと**エンデュアチャーム（HP満タンから即死する一撃をHP1で耐える）が
効いている。**4v4では最初の1匹を落とした側がそのままサイクルあたりの手数で
上回るので、**開幕の1匹を守り切るかどうかがそのまま勝敗になる。**

相性との比較も測った。炎 vs 水は持ち物の有無にかかわらず水が20戦全勝で、
**相性は持ち物より重い**。持ち物が変えるのは決着までの長さ（平均1.4→1.9
サイクル）。

### 残っている観測: ミラー戦がわずかに後手有利

選出と配置を揃えたあとのミラー戦を通算すると、先手側（自陣）60勝・
後手側87勝（147試合）。五分から -2.2σ で、**小さいが偏りがある可能性が高い。**
行動順は優先度→種族値→ランダムで、同値の乱数決着も対称に書けているので、
原因はまだ特定できていない。試合数を増やして切り分ける必要がある。

## 18. 構築画面（パーティ編成）

形はパーティ編成画面の定石にならう。**左に6枠の並び、右に選んだ1匹の中身。**
枠を押すと右が丸ごと入れ替わるので、6匹を見比べながら1匹を作り込める。

別画面へ飛ばさないのは、技を差し替えた結果が他の5匹とどう噛み合うかを
見ながら決めるものだから——飛ばすと毎回戻って確認することになる。
唯一フェーズを分けたのが種族選択で、これは287種の一覧が構築画面に
収まらないため（`SpeciesPickScreen`）。

```
相手選択 → 構築 ⇄ 種族選択 → 選出(50秒) → 配置(20秒) → 対戦(20分)
```

### 右側は3段

| 段 | 中身 |
|---|---|
| 種族 | 名前・属性・種族値(HP/攻/防/合計)・特性とその説明。「種族を変える」で種族選択へ |
| 技 | **learnset 全部**から4つ。選んだ4つは上に固定、残りは独立した枠でスクロール |
| 持ち物 | 16種から1つ。他の枠が持っていれば、押すとそこから移る（持ち替え） |

技の行は Lv / 属性 / 分類 / 技名 / 射程 / 威力 / 命中 / PP / ウェポンタグ /
優先度。数字が縦に揃うので、**威力帯の穴と射程の偏り**が並べただけで見える。

### レベルキャップは無視する

**対人戦では習得レベルを見ない。**learnset にある技はすべて選べる
（Lv50を超えるレベルで覚える技も含む）。Lv欄は「その技を最初に覚える
レベル」を出しているだけで、選べるかどうかには一切関係しない。

規則としては最初からそうなっていた（`BattleTeam.Validate` は learnset
所属だけを見て、レベルを見ていない）。画面がそれをそのまま見せる形にした。

### 4つ埋まったら押せなくする

技が4つ埋まると、選ばれていない技の行は `Disabled` になる。押せるのに
入らない、という状態を作らないため。外したい技を押せば1つ空くので、
そこで初めて他の技が押せるようになる。

### 規則の判定はUI側に書き直さない

構築画面の充足表示は `BattleTeam.Validate()` の結果をそのまま出す。
同一種族の重複・持ち物の重複・技4つ・6匹の登録の4項目で、違反した瞬間に
赤へ転じ「対戦を受け付ける」が押せなくなる。

種族の差し替え（`BattleTeam.SetSpecies`）は、**技を持ち越さない**。
learnset が変わるのでそのままでは learnset 外になる。NPCと同じ選び方
（`DefaultLoadout`）で4つ入れ直す。

持ち物（`BattleTeam.SetItem`）は、他の枠が持っていればそこから外して移す。
「重複しているので選べません」と拒むより、持ち替えとして通すほうが早い。

### 機械検証

| 検証 | 結果 |
|---|---|
| 構築画面に6匹ぶんの枠が並ぶ | OK（6枠） |
| 覚えられる技を全部出す(レベルキャップ無視) | OK（28/28件） |
| Lv50超で覚える技も選べる | OK |
| 技を押すと入れ替わる | OK |
| 技は4つを超えない | OK |
| 持ち物は重複せず持ち替えになる | OK |
| 種族を差し替えると技も入れ直す | OK |
| 種族選択で登録済みの種族は押せない | OK（5件） |
| 構築が違反していると開始できない | OK |

## 19. 完全ランダム構築での通しシミュレーション

構築（種族・技・持ち物）を毎試合ごとに完全無作為化し、AIの行動が
でたらめではなく構築の強さに意味のある形で応答しているかを、大量の
試合数で統計的に確かめる。

```
godot --headless --path . Scenes/BattleMatchScene.tscn -- --random --matches 100
```

`--random` を付けると `--home`/`--away`/`--items` は無視され、**毎試合ごとに**
自陣・敵陣とも一から無作為に組み直す。

- 6匹の種族は重複なくランダム
- 各自の技4つは、その種族の learnset から重複なくランダムに選ぶ
  （威力や属性で選ばない。`DefaultLoadout` / NPC生成器の「強い技を優先」
  とは別系統——今回は選り好みしないことが目的）
- 6匹**全員**に、対戦用持ち物16種から重複なく1つずつ**必ず**持たせる
  （持たせない選択肢は無い）

行動判断（選出・配置・毎ターン）は両陣営とも `NpcOpponent` の同じ1本の
判断ロジックを使う。**構築だけを無作為化し、判断は固定する**ことで、
勝敗が構築の強さに応答しているかどうかだけを切り出して見られる。

指標は「選出4匹の合計種族値が高い側が、実際に勝った側と一致した割合」
（`BattleMatchScene` が毎試合の実配置4匹から自動集計する）。50%前後なら
行動判断が機能していない証拠、有意に50%を超えていれば構築の強さを
活かせている証拠になる。

### headless モード

`BattleFlow.Begin(..., headless: true)` を付けると、`Show()` は画面
（`Control` ツリー）を一切作らない。`SpawnOrApply`・`BeginCycle`・
選出/配置の確定など**状態遷移は変わらず起きる**——スキップするのは
「見せるもの」だけ。

これが要る理由は素朴に重い。通し試合を何百戦も連続実行すると、1ターン
解決するたびに盤面56マス＋行動順レール＋名簿ぶんの `Control`/
`StyleBoxFlat` を作り直していた。見る人が誰もいない試合でこれを毎ターン・
毎試合作っては捨てるのは、対戦の骨格そのものより重い無駄な仕事だった。

| 100試合の所要時間 | 備考 |
|---|---|
| headless無し | 500秒以上でも完走しない |
| headless あり | 27秒 |

安全性は「`_hud`/`_screen` への書き込みはすべて `_hud?.`／
`if (_hud == null) return;` で守られている」という既存の実装に乗っている。
後者のガードで無効化される経路（`BeginActorPick` の「出せるパルが尽きた側は
空の提出を出す」など）は、いずれもボタン操作で駆動する対人UI専用の分岐で、
`BattleMatchScene` は `SubmitPlayerInput`/`NpcOpponent.Decide` を直接呼ぶ
経路しか使わないため影響しない（`NpcOpponent.Decide` 自身が「出せるパルが
いない」場合の空提出を返すので、UI側の自動提出に頼っていない）。
対人UIの経路（`BattleFlowScene` / `BattleTestScene` の対話的な検証）は
`headless` を渡さない（既定 `false`）ので、一切変わらない。

### 連続実行で後半だけ極端に遅くなる不具合（先に見つかったもの）

headless化の前に、もう1つ別の不具合を踏んで直した。`BattleScheduler` と
`NpcOpponent` が対戦のたびに専用の `RandomNumberGenerator`
（Godot管理下のネイティブオブジェクト）を `new` していた。どちらも
`Node` ではないただのC#オブジェクトなので、試合ごとに `host.Free()` しても
道連れにならず、.NETのGCが追いつくまで未解放のまま残り続ける。試合を
重ねるほど未解放オブジェクトが積み上がり、後半ほど遅くなっていた。
専用インスタンスを持たず、Godot本体の大域RNG（`GD.Randf()` /
`GD.Randi()`）を直接使うように変更した（同値時のランダム決着という
挙動は変えていない）。あわせて `RunMatch()` の `host.QueueFree()` を
`host.Free()` に変更した（`QueueFree` はフレーム末まで解放を遅らせるため、
フレームが一度も挟まらない一括実行では試合を重ねるほど未解放ノードが
積み上がる）。

**結論: AIは有意な（でたらめではない）行動を学習できている。**
構築（種族・技・持ち物）を完全に無作為化し、両陣営に同一の判断ロジック
（`NpcOpponent`）を与えても、勝敗は構築の強さに一貫して応答した。
選出・配置・毎ターンの行動判断のどこかで種族値や技の質を正しく
評価できていなければ、この相関は50%前後（バッチ間でばらつく雑音）に
埋もれていたはずである。4バッチとも独立に50%を上回ったことが、
単発の偶然ではなく再現性のある効果であることを裏付けている。

## 20. 「最も強い構築」100通りの総当たり

§19までは構築を完全無作為化して「AIの判断が構築の強さに応答しているか」
を見た。ここでは逆に**構築側を強い方へ寄せ、選出をさらに相手を見た相性
判断にした状態**で、強い構築どうしを戦わせたときに何が起きるかを見る。

```
godot --headless --path . Scenes/BattleMatchScene.tscn -- \
      --strongest --teams 100 --repeat 10 --shard K --shards N --out path.csv
python3 Tools/merge_strongest_results.py path --shards N
```

- 種族値（HP+攻撃+防御）上位60種のプールから、6匹を重複なく（伝説は
  1体まで）無作為に選び、技は `DefaultLoadout`（自属性最大威力→打点の
  重ならない他属性→残り威力順、§16と同じ選び方）、持ち物は対戦用16種
  から重複なく全員へ——という「強いと思える構築」を100通り組む。
  乱数シードを固定しているので、複数プロセスに分けても同じ100構築を
  再現できる。
- 100構築の全組み合わせ（C(100,2) = 4,950通り）をそれぞれ10戦——
  **合計49,500試合**。1戦ごとに先手/後手を入れ替え、先手側の利による
  偏りを消す。
- 選出は§16「選出の選び方」のとおり、両陣営とも相手の6匹（種族のみ）を
  見た相性判断。

計算量が構築数の2乗で伸びる（100構築で4,950ペア）ため、`--shard`/
`--shards` でプロセスを分けて実行した。4プロセスへ分割し、CPU4コアで
並列に実行（担当ペアの割り当ては `(i*構築数+j) % シャード数` で決まる
ので、シード固定と合わせれば分割数を変えても同じ結果になる）。

### 結果

| 指標 | 結果 |
|---|---|
| 総試合数 | 49,500（4,950ペア × 10戦） |
| 決着 | 47,733（96.4%） |
| 引き分け | 1,225（2.5%） |
| 未決着（600提出の上限） | 542（1.1%） |
| 決着までのサイクル（平均/最短/最長） | 8.4 / 1 / 500 |
| 勝率の分布（100構築） | 平均48.2% / 標準偏差18.8pt / 最高84.7% / 最低10.1% |

未決着は1.1%——§19（完全ランダム構築、0.72%）よりわずかに高い。双方とも
強い構築どうしがぶつかる分、決着が付きにくい組み合わせが増えるのは
自然で、根拠は同じ（1vs1終盤の削り切れない持久戦、`TurnCap` が正しく
上限として機能）。

**勝率は10.1%〜84.7%まで大きく開いた。**100構築とも同じ強いプールから
組んでいるにもかかわらず、上位と下位で7倍以上の差が出ている——「強い
種族を集めれば勝てる」わけではなく、**構築どうしの組み合わせ（誰が
誰に対して有利か）が勝率を大きく左右する**ことを示している。

**伝説タグの有無だけでは勝率を説明できない。**勝率上位20構築のうち
伝説を含むのは12/20、下位20構築でも12/20——ほぼ同じ比率（全100構築中
61構築が伝説を含む）。種族値上位プールという「すでに強い」母集団の中では、
1体の伝説が入っているかどうかより、6匹全体の相性・カバー範囲のほうが
勝敗を分けている。

**上位20構築と下位20構築で、よく現れる種族がはっきり分かれた。**

| 上位20構築での出現数上位 | 下位20構築での出現数上位 |
|---|---|
| リリクイン 8 | アイギルガ 8 |
| シェルガドラ 5 / ココヤンバ 5 | シャオロン 6 |
| ルナクイン 4 / センコ 4 / マグナイト 4 / イシス 4 / レイバーン 4 / キンガゼル 4 | トコナッツ 5 |

リリクインは上位20構築の40%に登場する一方、下位20構築にはほぼ現れない
——今回のプール・相性計算の下では明確に「刺さりやすい」種族だったと
いえる。逆にアイギルガ・シャオロンは下位に偏っており、種族値だけでは
強さが測れない（＝相性・技のタイプ分布まで含めた総合力で決まる）ことの
裏付けになる。

**結論: 種族値で「強い」種を集めるだけでは勝率は決まらない。**構築どうしの
相性——誰が誰に対して有利かという組み合わせの効果——が支配的で、
選出フェーズで相手を見て動くようにした判断（§16）と合わせて、対戦の
勝敗が構築内容と噛み合った形で決まっていることが確認できた。

## 21. 三すくみ（環境メタ）の発見

§20の100構築総当たりの結果を、勝率上位50構築のネットワーク図（各構築Aに
対して最も高い勝率で勝った構築Bを B→A の矢印で結ぶ）として可視化した
ところ、**#66 → #53 → #30 → #66 という循環**が見つかった。

| 対戦カード | 結果（10戦） |
|---|---|
| #66（総合48位）vs #53（総合49位） | 66が10-0 |
| #53（総合49位）vs #30（総合5位） | 53が10-0 |
| #30（総合5位）vs #66（総合48位） | **30が10-0** |

総合順位では66・53は下位（48・49位）、30は上位（5位）だが、勝敗はこの
3者の中で一方向には並ばない——66は53に完勝するが30には完敗し、53は30に
完勝するが66には完敗する、という正真正銘の三すくみ。種族値の合計では
測れない、構築どうしの組み合わせだけが生む効果であることが、この3枚
カードで最も鮮明に出ている。

3構築の中身（種族・技・持ち物）は§20と同じ乱数シード
（`MetaScenario.Seed = 20260822`）から再現できる——`MetaScenario`
（`Scripts/Battle/MetaScenario.cs`）に、§20の100構築生成手順と合わせて
切り出してある。

## 22. 環境メタへの対抗構築と、対戦中に適応する3すくみ

§21の三すくみを「環境メタ」の基準として固定し、(a) それに対抗する構築を
新たに30種類考案し、(b) 三すくみの3構築だけには対戦を通じた適応（技・
持ち物の変更、個体＝種族は変えない）を許可した上で、33構築（3+30）の
総当たりを行った。

```
godot --headless -- --meta-core --challengers 30 --loop-size 5 --loops 4 --out path.csv
godot --headless -- --meta-challengers --challengers 30 --shard K --shards N --out path.csv
python3 Tools/analyze_meta_results.py <出力先ディレクトリ>
```

### 対抗構築の探索

種族値上位150種（§20の60種より広いプール——カウンター探索は生の強さより
相性を優先するため）から、§20と同じ「強い構築」の組み方（`DefaultLoadout`
＋持ち物の重複なし配布）で6匹を組み、三すくみの3構築それぞれに対する
有利度を見積もる。

```
有利度(候補, 相手構築) = Σ 候補の6匹 × 相手の6匹 の全組み合わせ (
    候補側の最強打点 × 相手の属性への相性倍率      … 通りやすさ
    − 相手の属性が候補に通る倍率 × 40              … 受けやすさ
)
```

§16「選出の選び方」と同じ式を、1対6（選出時）から6対6（構築どうし）に
広げただけ——物差しは共通にしてある。この有利度が0より大きければ
「有利」とみなし、**3構築のうち2体以上に有利な構築だけ**を対抗構築の
候補とする。

見つかった候補は「どの2/3体に有利か」のカテゴリ別に均等採用するよう
設計したが、実際に見つかった候補はすべて**3体全部に有利**という
カテゴリに属した——種族値上位150種という広いプールからは、三すくみの
特定の1〜2体だけでなく全体に噛み合う構築のほうがむしろ見つけやすかった、
ということ。この中から有利度の合計が高い順に30構築を採用した。

### 三すくみ側の適応

三すくみの3構築（種族＝個体は固定）は、対戦相手ごとに5戦のループを
4回（計20戦）行う。**ループの勝率が60%を下回った場合に限り**、そのループ
で最も多く倒れた1匹について、次のいずれかを試みる（技を優先、無ければ
持ち物）。

- **技**: 今の4技のうち相手への通りが最も悪い1つを、learnset内の未採用技
  で最も通る技に差し替える——ただし15%以上の改善が無ければ変えない。
- **持ち物**: 相手のいずれかの属性が2倍以上通っている（弱点を突かれている）
  なら「ウィークシェル」。既に何らかの耐久札を持っているなら変えず、
  無ければ「ラストトニック」系の耐久札を優先で持たせる。

変更は次の対戦（同じ相手との次のループ、または次の対戦相手）にも引き継ぐ
——`BattleEntry.MoveIds`/`ItemId` を直接書き換えるので、同じ `BattleTeam`
オブジェクトを対戦のたびに使い回すだけで自然に持ち越る。

**この適応は状態を引き継ぐため、shard分割できない**（並列化すると
どの試合がどの順で起きたか壊れる）。3すくみ内3ペア＋メタ×対抗構築30件
=93ペア×20戦=1,860試合を単一プロセスで順に処理する。対抗構築どうしの
435ペア（8,700試合）は適応が絡まないので、§20と同じ形でshard分割した。

### 結果: 33構築・528ペア・10,560試合

| 指標 | 結果 |
|---|---|
| 総試合数 | 10,560（528ペア×20戦） |
| 決着 | 10,267（97.2%） |
| 引き分け | 182（1.7%） |
| 未決着 | 111（1.1%） |
| 決着までのサイクル（平均/最短/最長） | 8.5 / 1 / 494 |
| 適応イベント数 | 40（技の差し替え31・持ち物の差し替え9） |

**三すくみは適応後もほぼ崩れなかった。**#66 vs #30 は20戦中1勝19敗
（適応前・静的10戦では0勝10敗）——技の差し替えを4ループ試みても、
1勝を拾えた程度で決着的な改善にはならなかった。個体（種族・タイプ）を
変えられない以上、技と持ち物だけでは埋まらない相性差がある、という
ことがはっきり出た。#66 vs #53（20-0）、#53 vs #30（20-0）は変わらず
一方的なまま。

| 三すくみ | 対32構築の通算成績 | 勝率 |
|---|---|---|
| M2（#30） | 520勝103敗12分5未決着 | **81.2%** |
| M1（#53） | 412勝210敗8分10未決着 | 64.4% |
| M0（#66） | 410勝218敗6分6未決着 | 64.1% |

三すくみ内でM0はM1に完勝するにもかかわらず、対32構築の通算勝率は
M1のほうがわずかに高い——**直接対決の勝ち負けは、フィールド全体での
強さの順位を保証しない**、という§20の教訓がここでも成り立っている。

**対抗構築の「狙い通り」は、大半が外れた。**生成時点では30構築とも
三すくみ全3体に有利と判定していたが、実戦（各20戦）で実際に勝ち越せた
のは平均で3体中0.60体——2体以上に有利という前提を満たした構築は
**1つも無かった**（3/3命中はゼロ、2/3命中は4構築のみ: C1・C6・C9・C28）。
残り18/30構築は、狙ったはずの3体すべてに逆に負け越した。

**属性の相性だけを見積もる有利度の式は、実戦の勝率を大きく過大評価する。**
命中打点と被弾倍率だけでは、対戦順（先手/後手）・急所・状態異常・
持ち物の発動条件・AIの選出/行動判断の質など、実際の勝敗を左右する要素の
大部分を無視しているため——§16の選出スコアで使うぶんには「同じ物差しで
選ぶこと」自体に意味があったが、**構築の設計段階で使う「予測」としては
過信できない**という限界が、大規模な実戦検証によって定量的に示された。

**それでも、狙いが外れた構築の中から結果的に強い構築が出た。**総合勝率
ランキングでは、対抗構築のうち4件（C4・C9・C1・C14、65〜75%）がM0・M1
より高い通算勝率を記録し、C4（74.7%）はM2（81.2%）に迫った。**設計時に
狙った相性が外れても、6匹全体としては別の理由で強い構築になっていた**
——という、相性予測と実際の強さが必ずしも一致しないことの、もう1つの
側面。

**結論: 対戦中の適応（技・持ち物の変更）は、個体を変えられない場合、
根本的な相性差を覆すには力不足。**一方で、事前の相性予測（属性の
組み合わせだけを見る式）は対戦結果の複雑さを大きく取りこぼす——
実際に大量に戦わせてみて初めて「本当に効く構築」が分かる、という
身も蓋もない、しかし対戦ゲームとして自然な結論になった。
